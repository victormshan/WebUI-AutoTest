# 合规状态：Gemini 网页通道

状态：**已决定（2026-10-12）**：选（a）。用户原话「全部同意」，即同意 Claude 的建议。技术 PASS（A1）不等于合规 PASS。

## 已知事实
- **审核主通道已改为 Gemini API**（2026-10-11 用户决定；2026-10-12 已生效，模型 gemini-3.8-flash，强度 external-api 4）。网页通道只作为 API 不可用时的回退。
- **现有的网页回退**是 DSH 的 Chrome 扩展通道（web-gemini，运行在 Windows 上），已经在用。A2 打算用 Native Runtime 改造它，或者与它并存。
- Google 条款对自动化访问服务有限制，具体是否适用于本用法，**需要用户核查**。
- **A1 实测到的平台态度：**
  - 带调试参数时**拒绝登录**（"This browser or app may not be secure"）；
  - 已登录会话**连续自动使用约 25 分钟、5 轮后，触发异常流量验证页**（`google.com/sorry/`）。
  - 这说明平台在主动识别并限制这类自动化。
- 账号：A1 用的是用户提供的专门账号。

## 需要用户决定
1. **网页通道是否继续保留为审核回退？**
   - **（a）** 保留现有的扩展通道（web-gemini），不做 A2；
   - **（b）** 做 A2，用 Native Runtime 替代或补充扩展通道，并严格低频（见 runbook 第 3 节）；
   - **（c）** 网页通道全部停用，审核只用 Gemini API（API 不可用时报 unavailable，任务暂停，等 API 恢复或交给人）。
2. 如果选（a）或（b）：确认已核查适用条款并接受账号风险；确认使用专门账号；确认频率上限 N 和被风控后的冷却时长。
3. 组织授权：如果这个仓库或账号属于某个组织，是否需要该组织的书面同意。

## Claude 的建议（供参考）
主通道已经是 Gemini API，网页通道又在 A1 里暴露出登录拦截和使用风控两道限制，所以从风险和收益看，**倾向（c）或（a）**：保持现状，不扩大网页自动化。A 线的技术成果（pipe Runtime）保留下来，转给 B 线（webtest 后端，面向用户自己的站点，不涉及第三方条款）。选（b）也可以，但定位只能是低频、可停用的回退。

## 决定（2026-10-12）
- **选（a）：维持现状。** 审核主通道是 Gemini API（新增对 503/429 的有限重试，`bea0a22`）；回退仍是 DSH 现有的扩展通道 web-gemini，**不扩大网页自动化，A2 不做**。
- 没选（c）的原因：今天 Gemini API 多次返回 503，如果没有任何回退，审核会频繁暂停。加了重试之后，如果回退次数明显减少，可以再评估改成（c）。
- 账号与条款风险：现有扩展通道一直在用，这是用户已知并接受的状态；这次决定没有增加新的网页自动化。
