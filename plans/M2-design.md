- 阶段登记；
- 请求与作业；
- 输入快照与绑定；
- 签名记录（哈希链）；

- 状态推导；

- 同步与检查点；

- 停止规则；

**不做**（方案第 5 节"延期"）：

- 模型 B。

## 2. 角色与信任边界（模型 A）
- **gate**：服务以 `reviewgate` 身份运行，是唯一的签名者，也是记录的唯一追加入口（见 3.7）。
- **runner**：只执行作业、计算输入摘要、报告运行结果，不判断放行。
- **实施方**（Claude，administrator）：
  - 申请登记阶段、发起请求、取消自己的请求；
  - 把 gate 已签名的日志写入 notes 并推送（gate 没有推送凭据）；
  - 不能写 gate 的状态，也不能伪造签名。
- **用户**：通过 `sudo -u reviewgate review-gate admin …` 在本地操作，属于 A 级（可追责、身份不可验证），与现有 `admin manual` 相同：
  - 确认阶段登记（任务书与条件）；
  - 豁免条件、撤销、恢复暂停的阶段；
  - 修改厂商表。
- **远端**：gate 在配置里固定仓库 URL（`https://github.com/victormshan/WebUI-AutoTest.git`），用自己私有的 bare 缓存（`state/milestones/remote.git`）匿名 fetch `refs/notes/review-gate-milestones`。它不受实施方 `origin` 配置的影响，也不需要凭据。
  - 匿名读取已以 administrator 身份实测可用（`plans/M2-evidence/anonymous-read.txt`），以 reviewgate 身份的实测放进实现验收。
  - **审计正文会公开**（公开仓库），需要用户确认，见第 8 节 U1。

## 3. 数据模型
### 3.1 阶段登记
阶段在使用前必须登记，登记分两步：
1. **实施方申请**，提供：
   - 稳定的阶段 id（满足 `valid_id`）；
   - 仓库标识；
   - 任务书路径及其在 `base` 中的内容哈希；
   - 验收条件（文字，gate 为每条分配 id，作为初始的阻断条件）；
   - 基线提交 `base`；
   - 来源声明：bridge 上与本阶段关联的方式，见 3.6。
2. **用户确认**：`admin milestone confirm <phase>`，确认后写入 `phase_registered` 记录。未确认的阶段不能发起请求。

登记后，阶段 id、仓库、`base`、任务书哈希都不能改。要改只能登记一个**取代它的新阶段**。新阶段的登记申请必须引用被取代的阶段，确认时用户能看到。

**取代时默认延续**以下内容：
- **计数**照常累加；
- **被取代阶段所有未解除的阻断条件**原样延续到新阶段，id 不变，对新阶段同样起阻断作用；
- **实施来源**：被取代阶段已认定的参与者（提交作者、尾注、bridge 任务）全部并入新阶段的参与者集合，所以同厂商的检查仍然有效。

如果范围变化让某条旧条件或某个来源不再适用，必须由用户**逐项**处理：
- 条件用 `admin milestone waive`（理由写明"因阶段取代不再适用"）；
- 来源用 `admin milestone drop-source`。

每项操作各留一条记录。**确认新阶段的登记，不等于豁免任何条件或来源。**

### 3.2 请求的范围
- 每次请求给出 `head`。gate 检查：
  - `base` 是 `head` 的祖先；
  - `base..head` 内的**每个提交（包括合并提交）**都有有效的提交审核签名。
- 合并提交按 `git rev-list base..head` 全部纳入，不跳过。
- 同一阶段的后续请求只能把 `head` 往前推（新 head 必须以旧 head 为祖先），否则拒绝。

### 3.3 记录：只追加、哈希链、逐条签名
公共字段：

```
format     记录格式版本（首版 1）
seq        从 1 开始，连续
prev       上一条的 hash（第 1 条为 64 个 0）
at         gate 时间（UTC）
repo       仓库标识
key_id     签名公钥的 sha256 前 16 位
kind       见下
phase      阶段 id
body       按 kind 不同
hash       sha256(JCS 规范化 JSON，不含 hash/sig)
sig        gate 的 ed25519 签名（对 hash）
```

规范化用 RFC 8785（JCS）：键排序、数字和字符串按 JCS 规则序列化。

`kind` 有：
- `phase_registered` / `phase_superseded`：阶段登记、被新阶段取代。
- `baseline_changed`：用户认可的新任务书版本（内容哈希、在哪个提交中），见 4.1。
- `source_dropped`：用户逐项去掉一个不再适用的来源（随阶段取代而来的）。
- `task_linked` / `task_ignored`：用户把一个"未匹配"的 bridge 任务关联到本阶段，或写明理由后忽略它（第 3.8 节）。
- `request`：发起一次审计。body 包含：
  - `request_id`；
  - `head`、`tree`（head 的树哈希）；
  - **基准版本**：当前生效的 `phase_registered` 或 `baseline_changed` 记录的 seq，以及任务书内容哈希；
  - 输入快照清单（每个文件的路径、大小、sha256）、最终输入的大小和 sha256；
  - 指令模板版本与摘要；
  - 参与者、映射结果、厂商表版本与内容哈希；
  - 审计者；
  - runner 期望的身份；
  - 当前计数与阈值。
- `job`：runner 的回复原样记录（所有字段，包括 `answer` 全文），外加 gate 核对的 runner 身份（见 5）。
- `audit`：gate 对答复的解析结果，包括：
  - verdict：APPROVE / APPROVE WITH CONDITIONS / REWORK / BLOCK / `invalid`；
  - 新条件（由 gate 分配 id）；
  - RESOLVED 声明。
- `request_closed`：请求进入终态（completed / failed / timed_out / cancelled）及原因。**终态只写一次，之后不能改写**。
- `condition_resolved`：审计确认条件已满足，引用条件 id 和作出确认的 `audit` 记录。
- `condition_waived`：用户豁免，带理由。
- `revoke`：撤销该阶段当前的放行（用户）。
- `resume`：用户恢复已暂停的阶段。
- `vendors_changed`：厂商表的新版本与内容哈希（用户）。
- `published`：实施方报告已推送到哪一条 `(seq, hash)`。gate 核验之后才写 `archived`。
- `archived`：gate 核验远端后确认的检查点 `(seq, hash)`。

### 3.4 状态推导（纯函数，输入是同一份已核验快照）
把"状态"和"放行"分开：

**① 状态用全部已核验记录推导，不管有没有归档。** 包括：
- 当前请求（最新的 `request`）、请求终态；
- 取消、撤销、暂停；
- 未解除的条件；
- 计数。

所以一条**未归档的新请求或撤销，会立即让旧批准失效**。

**② 放行**：只有当下列各条同时满足时才放行：
1. 阶段已登记、已确认，没有暂停；
2. 当前请求的终态是 completed；
3. 它的 `audit` 是 APPROVE 或 APPROVE WITH CONDITIONS；
4. **无论哪种批准，阶段都没有未解除的阻断条件**（包括登记时的验收条件和历次审计提出的条件）；
5. 当前请求之后没有 `revoke`，**也没有 `baseline_changed`**；当前请求绑定的基准就是阶段当前生效的基准；
6. 独立性检查通过；
7. **归档条件**：促成放行的每一条记录都已归档（seq ≤ 检查点）。这些记录包括：
   - 当前请求、它的 job、audit 和终态；
   - 解除所有阻断条件的 `condition_resolved` 和 `condition_waived`；
   - 消除"来源未知"所依赖的 `source_dropped`、`task_linked`、`task_ignored`；
   - 阶段登记、当前生效的 `baseline_changed`。

   **未归档的批准或豁免不能产生放行。**

**③ 有效性规则**：
- **基准变更**：`baseline_changed` 一写入（即使还没归档），就有以下效果：
  - 阶段当前的放行立即失效；
  - 绑定旧基准的请求，只要还没进入终态，就以 `cancelled`（原因：基准变更）结束；
  - 之后到达的结果按"迟到"处理；
  - 要再次放行，必须用新基准发起新请求。

  基准变更**不会**清零计数，**也不会**解除任何旧条件。
- 只有**当前请求**的有效 audit（解析成功、版本绑定一致：`input_sha256`、job_id、head、tree 都与 request 记录相符）才能：
  - 解除条件；
  - 改变当前请求的终态；
  - 增加计数。
- **迟到的结果**（请求已取消、已超时、已被新请求替代）照样作为 `job` 和 `audit` 记录存档，但：
  - 不能解除条件；
  - 不能改变任何状态；
  - 不计数。
- 条件：
  - 阻断条件一直保持未解除，直到出现引用它 id 的有效解除记录；
  - 审计没有提到某条件，不等于解除；
  - 条件的两种解除方式分开显示。

**④ 停止计数**：
- 按阶段 id 计数，阶段被新阶段取代时计数随之延续。
- 当前请求的有效 audit 给出 REWORK 或 BLOCK 时加 1；`invalid`、运行失败、迟到的结果不计数。
- 放行或用户 `resume` 时清零。
- 达到阈值 3 时进入暂停：不能发起新请求，直到用户 `resume`。

### 3.5 发布、归档与检查点
- **本地**：
  - `state/milestones/log.jsonl`（只追加，每行一条，写入后 fsync）；
  - `state/milestones/checkpoint.json` 保存检查点。
- **notes 的表示**：整份日志作为一条 note，挂在固定的锚点对象上（内容为 `review-gate-milestones anchor v1` 的 blob，gate 和客户端都能算出它的 id）。
- **发布**（`review-gate milestone publish`，实施方执行）：
  1. 向 gate 取当前日志（含签名）；
  2. 先 fetch 远端的 notes，**如果远端日志不是这份日志的前缀，就拒绝**，绝不覆盖更新的远端；
  3. 写 notes 并普通推送（不使用 `--force`）；
  4. 报告 gate 推送到了 `(seq, hash)`，gate 写一条 `published` 记录。
- **归档确认**：
  1. gate 用私有缓存 fetch 远端；
  2. 按 3.6 的规则核验；
  3. 确认远端包含到 `(N, hash)` 的记录，写 `archived(N, hash)` 并更新检查点。
- **防止无限补推**：`published` 和 `archived` 是簿记记录，不在放行所需的归档集合里（第 3.4 节 ② 第 7 条）。它们会随下次发布带上去，但放行不等待它们自己归档。

### 3.6 同步（每次推导状态前执行）
设本地日志为 L，远端日志为 R。每次都逐条验签、验证哈希链，并检查格式版本和 `key_id`：
- **L == R**：直接推导。
- **R 是 L 的前缀**：
  - L 多出的部分是"未归档尾部"：参与状态推导（第 3.4 节 ①），但不能产生放行（第 3.4 节 ② 第 7 条）；
  - 如果检查点 seq > |R|（已确认归档的记录远端却没有），**全部停止放行**。
- **L 是 R 的前缀**：先核验 R 多出的记录，再追加到 L；追加完成之前不放行。
- **分叉、核验失败、远端不可达**：**全部停止放行**，状态显示原因，交给用户处理。
- **检查点**：
  - R 必须包含检查点，且检查点之后的部分链条连续有效；
  - 允许 R 继续增长；
  - 只有 R 比检查点短、检查点位置的 hash 不符，或者链条校验失败，才停止放行。
- 推导用这一次核验得到的**同一份快照**；返回的状态附带快照的 `(seq, hash)`。

### 3.7 唯一追加入口、并发与崩溃恢复
- 所有写记录的操作都经过同一个函数，在同一个跨进程文件锁（`state/milestones/log.lock`，flock）下完成，包括服务和本地 admin 命令。顺序是：读尾部 → 校验 → 追加 → fsync。
- **崩溃恢复**：
  - 启动时或每次加锁后验证整条本地链。如果最后一行不完整（崩溃中断），**不自动截断**，全部停止放行，交给用户处理。
  - 写入顺序固定：先追加 `archived` 记录并 fsync，再原子地（写临时文件、fsync、rename）更新检查点文件。所以正常的崩溃间隙只有一种：**日志领先**，即日志里最后一条 `archived` 比检查点文件新。
  - **日志领先、且那条 `archived` 可以验证**（签名有效、在链上、它指向的 `(seq, hash)` 在本地链中）：用它重建检查点文件。
  - **检查点文件领先**（它的 seq 大于日志里任何 `archived`，或者本地链比检查点短）、**同一位置的哈希冲突**、**无法比较**：**停止放行**，并向远端核对。远端能证明检查点（远端链含有检查点 `(seq, hash)`），才继续——这时先从远端补齐本地链，补齐后再验证；否则交给用户处理。**绝不静默降低检查点**，以免失去发现远端回滚的依据。
  - 测试覆盖：
    - 两种写入间隙：`archived` 已写、检查点未更新；检查点临时文件已写、尚未 rename；
    - "日志回退、检查点仍较新"；
    - 检查点哈希冲突。

### 3.8 来源与独立性
- **参与者来源**：
  - `base..head` 内每个提交的作者和 `Co-Authored-By` 尾注；
  - bridge 上与本阶段关联的任务的参与者。
- **bridge 任务的完整性**：两种方案，需要用户决定（第 8 节 U2）：
  - **方案 A（推荐）**：给 gate 一个只读的 bridge 观察者身份，由 gate 自己按阶段查询关联任务，不靠实施方声明。
    - 关联规则：任务 id 以 `<phase>-` 开头，或者 `parent` 链指向这类任务；被取代阶段的关联任务一并计入。
    - 查询不到 bridge 时，状态为"来源未知"，停止放行。
    - 名称关联**不能证明**全部实施工作都已列入，因此 gate 还会列出以下情况，**只要存在就显示"来源未知"并停止放行**，由用户处理：
      - **未匹配的实施类任务**：在阶段时间窗口内（从登记到 head 提交之间）由实施方接收或发出、但没有匹配到任何阶段的 task；
      - **断裂的 parent 链**：parent 指向不存在的任务；
      - **被取代阶段的任务**未被纳入。

      用户可以用 `admin milestone link-task` 或 `admin milestone ignore-task`（写明理由）逐项处理，每项留一条记录。查询成功不等于来源完整。
    - 需要给 agent-bridge 加一个只读角色，这是一项额外的小改动。
  - **方案 B**：首版接受实施方自报的任务列表，状态里注明"来源由实施方声明、完整性未核实"。这是一项验收变更，**必须由用户明确批准**，不能自动算进模型 A。
- **厂商表**：`state/milestones/vendors.json`，带版本号和内容哈希，每次修改都写一条 `vendors_changed` 记录（用户操作）。首版内容（DSH 的归属已由用户确认）：
  - `claude*`（含 Co-Authored-By "Claude …"）→ anthropic；
  - `codex`、`auditor` → openai；
  - `dsh` → deepseek；
  - 用户本人（git 作者 victormshan）→ `user`。
- **规则**：
  - 审计者与任一参与者同厂商：不放行；
  - 有参与者映射不到厂商：不放行；
  - 有提交缺少提交审核签名：不放行；
  - 来源未知（方案 A 下查不到 bridge）：不放行。

## 4. 输入与审计输出
### 4.1 输入快照（不删减、超长即拒绝）
1. **快照**：发起请求时，gate 把所有材料复制进自己的 `state/milestones/inputs/<request_id>/`，之后不再变，并逐个计算摘要。材料包括：
   - **任务书的基准版本**：用户认可的版本，按登记或最近一条 `baseline_changed` 记录的内容哈希，从对应提交读取。**审计始终附上这个基准版本。** 如果 `head` 里的任务书和基准不一致，就把 head 版本作为"修订材料（未经用户认可）"另附，并在指令里写明：验收依据是基准版本，修订材料只作参考。要让修订生效，先由用户 `admin milestone rebaseline` 认可，写入 `baseline_changed` 记录。
   - 证据文件（从 `head` 的指定目录读取，只认已提交的文件）；
   - `base..head` 的 diff；
   - 各提交的提交审核签名；
   - 未解除的条件列表；
   - 参与者映射说明。
2. **组装**：按固定模板（带版本）组装成最终输入，**按最终序列化后的大小**检查上限（runner 的 4 MB）。**超过上限就拒绝请求**，不删减、不只附摘要。
3. **缩小范围**：只能通过受控的阶段拆分，即登记取代当前阶段的新阶段（第 3.1 节）。未解除条件、实施来源和计数照常延续。不能缩小同一阶段的 head 区间：base 固定，head 只能前进。
4. **明确列出未提供的内容**：输入中没有附上的东西（例如二进制文件），在输入里明确列为"未提供"，不能当作已审查。

### 4.2 输出格式（要求审计者遵守）
```
VERDICT: APPROVE | APPROVE WITH CONDITIONS | REWORK | BLOCK
CONDITIONS:
- [new][blocking] <文字>
- [new][non-blocking] <文字>
RESOLVED:
- <条件 id>: <依据>
```
- gate 只解析这几段，正文原样保存在 job 记录里。
- 以下情况判为 `invalid`：
  - 缺少 VERDICT 或有多个 VERDICT；
  - APPROVE 却带有新的 blocking 条件；
  - RESOLVED 引用了不存在或已解除的条件 id。
- 审计输出漏掉旧条件，不会让它解除（第 3.4 节 ③）。

## 5. runner 连接与反向认证（M1 遗留）
**实测发现**（`plans/M2-evidence/peercred-probe.txt`）：通过 systemd 激活的 socket 连接时，客户端用 `SO_PEERCRED` 看到的是**创建监听 socket 的 systemd 管理进程**，不是 runner。所以不能用它做反向认证，也不能为此放宽检查。

**方案**：gate 在连接上设置 `SO_PASSCRED`，读取 runner 回复时，内核会附上**发送者的真实 pid、uid**（`SCM_CREDENTIALS`）。实测表明：
- runner 收到的是自己服务的 cgroup；
- 伪造 pid 会被内核拒绝（EPERM），而真实凭据照样到达。

gate 核对：
- uid = 997；
- 该 pid 的 cgroup = `/system.slice/audit-runner.service`；
- pid 在收到回复时仍然存活。

不符合就判为运行失败，记入 job 记录。

实现要求：
- 整条回复都用 `recvmsg` 读取，**每一段数据都必须带凭据**，并且各段凭据一致；
- 以下情况一律判为认证失败：缺少凭据、控制消息被截断（`MSG_CTRUNC`）、各段身份不一致、凭据的 pid 在读完时已不在 runner 的 cgroup 中；
- 不能只认证第一段，后面改用普通读取。
- runner 这一侧：继续用 `SO_PEERCRED` 核对 gate。runner 是 accept 的一方，看到的是 gate 的真实凭据，M1 已实测。
- **实测验收项**：
  - 正式激活路径下（跨 UID：gate 999、runner 997），gate 实际取得的凭据（uid、pid、cgroup）要记录下来；
  - runner 在回复后立即退出时的竞态（pid 已不存在）：必须判为认证失败，不能误判为通过；
  - 真实 gate 连接被 runner 接受；
  - gate 拒绝冒充的 runner：用一个别处监听的 socket，以其他用户或其他服务身份运行。

## 7. 测试与验收
- **单元测试**：
  - 状态推导（纯函数）；
  - 同步与检查点；
  - 解析；
  - 哈希链、签名、JCS；
  - 独立性；
  - 锁与崩溃恢复。
- **对照测试**：
  - 未归档的新请求或撤销会让旧批准立即失效；
  - 未归档的批准或豁免不能产生放行；
  - APPROVE 不能绕过旧的阻断条件；
  - 迟到的结果不能解除条件、不计数；
  - 终态不能被改写；
  - 改名或缩小范围不能清零计数；
  - 改名（阶段取代）后，旧的阻断条件和同厂商的参与记录仍然有效；
  - head 修改了任务书但没有重新认可时，审计依据仍是基准版本；
  - 基准变更：已有批准后变更、作业执行中变更、变更尚未归档——三种情况下旧审计都不能放行，迟到结果不能解除条件，计数和旧条件不变；
  - 未归档的 `source_dropped`、`task_linked`、`task_ignored` 不能消除阻断原因，也不能产生放行；
  - 检查点：两种写入间隙、日志回退而检查点仍较新、哈希冲突；
  - 反向认证：缺少凭据、控制消息截断、各段身份不一致、runner 已退出。
- **故障注入**，至少覆盖（方案第 5 节）：
  - 解析失败；
  - 迟到；
  - 旧输出替换；
  - 条件漏报；
  - 正常的未归档尾部；
  - 本地是旧的批准，而远端已撤销或已有新请求；
  - 远端截断；
  - 远端正常延长（不能误报）；
  - 分叉；
  - 远端不可达；
  - 签名被篡改。
- **M1 遗留**：
  - 清扫失败路径（A25）；
  - 真实 gate 连接 runner；
  - 反向认证拒绝冒充者；
  - 以 reviewgate 身份匿名读取远端。
- **变异测试**。
- **端到端**：见第 8 节 Q5。
