## 4. 里程碑审计的设计要点
1. **gate 就是监督进程，只有 gate 签名。** 审计执行器 `audit-runner` 没有任何密钥，以 `auditor` 用户运行 Linux 版 Codex（只读沙箱、不批准任何操作、材料从 stdin 输入）。
2. **通信**：
   - gate 和 runner 通过 unix socket 双向核对身份（`SO_PEERCRED`）和程序白名单；
   - runner 自己计算实际收到的输入的摘要；
   - 结果封装成结构化消息，模型的正文只放在 answer 字段里；
   - 以下情况都判为运行失败：CLI 非零退出、缺少输出文件、两处输出的结论不一致。
3. **验收请求**：每次审计都是一个请求，状态为 `pending → completed | failed | cancelled | timed_out`。**放行只看当前这个请求**：
   - 失败、超时、取消、迟到的输出、撤销：都不放行，也**不回退**到更早的批准；
   - 撤销之后，只有新的请求成功才能重新放行。
4. **条件账本**：
   - 条件 id 由 gate 分配；阻断条件会一直保持未解除，直到有引用它 id 的解除记录；
   - 审计输出漏报某条条件，不代表它已解除；
   - 解除分两种：`resolved_by_audit`（审计确认满足）和 `waived_by_user`（你决定豁免），分开显示；
   - 解析失败或结论自相矛盾：不放行。
5. **记录**：
   - 所有记录都只追加，做成哈希链，并且逐条签名；状态由记录推导；
   - 记录写进 `refs/notes/review-gate-milestones` 并推送；**没有确认归档就不放行**。
6. **本地与远端的同步**（每次推导状态前先执行）：
   - 两边相同：逐条验签后推导状态；
   - 远端是本地的前缀：本地多出的未归档记录保持"待归档"并补推。如果有记录已确认归档、远端却没有，**全部停止放行**；
   - 本地是远端的前缀：先核验远端多出的记录，再补到本地，补完之前不放行（所以撤销和新请求一定会生效）；
   - 分叉、核验失败、远端不可达：**全部停止放行**，交给你处理；
   - **检查点**（已按 Codex 的条件修正）：每次确认归档时，记下远端当时最后一条记录的序号和哈希。以后的远端**必须包含这个检查点**，并且之后的记录连续有效，**允许继续增长**。只有远端比检查点短、检查点位置的哈希不符，或者链条校验失败，才停止放行。
   - 推导状态时，使用经过核验的**同一份记录快照**，避免并发的新请求或撤销之后仍然返回旧的放行状态。
7. **独立性**：
   - gate 维护有版本的"参与者 → 厂商"声明表；每次审计的输入里写明当时用的版本；
   - 阶段参与者的来源有：提交作者、Co-Authored-By 尾注、bridge 镜像中的实施类任务；
   - 审计者与任一参与者同厂商、有参与者无法映射到厂商、有提交的来源不明：都不放行。
8. **停止规则**：
   - 按稳定的阶段 id 和它的整条重审链计数，只有得到放行才清零；
   - 有效审计给出 REWORK 或 BLOCK 才计一次；运行失败只记录，不计数；
   - 达到阈值就暂停，交给你决定。
