=== Commit version 4 (gate task m2-step6b-send-boundary, base e93dd92) ===
Answers Codex n=19 on e93dd92: the job thread's halt check and the actual start of the runner
call shared no synchronization boundary. Now runner::call is split into send (connect, write the
request line) and receive (read the reply). The job thread checks the snapshot outside the lock,
then under the admission lock rechecks `halted` and writes the line; it waits for the reply
outside the lock. A job counts as sent only once its line is written under the admission lock.
halt() takes the same lock, so either the line was fully written before halt() returns, or it is
never written.
Test-only hooks (cfg(test)) force each ordering deterministically:
- a_halt_just_before_the_send_keeps_the_job_from_going_out (before_send): no runner call, no job,
  request stays Pending.
- a_halt_while_the_line_is_written_waits_for_the_send (while_sending): halt() is still blocked
  after 300 ms and returns only after the line is written; the runner got exactly one call.
- a_halt_during_the_request_commit_waits_and_the_job_is_not_sent (before_commit): halt() is
  blocked after 300 ms; the request is committed; its job is not sent.
